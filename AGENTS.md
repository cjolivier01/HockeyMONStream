# Repository Guidelines

## Skills
- Some skill scan be found in the files and dirs under the 'skills' dir

## Project Structure & Modules
- Code: `src/` with libraries in `src/libs/*`, apps in `src/apps`, optional plugins in `src/gst-plugins`.
- Build files: `BUILD.bazel` next to sources; external repos in `WORKSPACE.bazel` and `buildfiles/`.
- Configs and assets: `configs/`, `env/`, `scripts/`, `docs/`.
- Tests: colocated with libraries (e.g., `ScoreboardTest.cpp`) and built as Bazel targets.

## Build, Test, and Run
- Debug build (all): `./bld` or `bazelisk build --config=debug //...`.
- Release build (all): `./perf` or `bazelisk build --config=opt //...`.
- x86_64 build: `bazelisk build --config=opt --cpu=k8 //...`.
- ARM64/SBSA build (native non-Jetson, e.g. GB300): `make arm64` or `bazelisk build --config=opt --config=arm64 //...`.
- Jetson (aarch64) build: `bazelisk build --config=jetson //...`.
- Before opening or updating PRs, validate changes on this machine with the x86_64 build and also validate ARM64/Jetson builds. A Jetson host is available at `stubby` for Jetson-specific build checks.
- Canonical runs:
  - End-to-end wrapper (recommended): `./run.sh --game-id=<game_id> -t=5`
    - Runs stage `0` (main pipeline) by default; if stitching artifacts are missing, one-pass stitching configures them in-process before allocating the `hmstitcher` output pool.
    - To run the older two-stage flow, pass `--two-stage` (stage `-1` stitching/rink-mask configuration with `FAKE`, then stage `0` main pipeline).
    - Supports `-t N`, `-t=N`, or `--time-limit=N`.
    - If configured pretrained assets are missing, it will download the assets declared in YAML `pretrained-assets`.
  - Direct `hstream-cli` invocation (useful for debugging configs):
    - Display only: `bazel-bin/src/apps/hstream-cli/hstream-cli -g <game_id> --enable-sources=URI-MULTIPLE --enable-sinks=RENDER --options=pipeline.hmaudio.enable=1`
    - Encode to file: `bazel-bin/src/apps/hstream-cli/hstream-cli -g <game_id> --enable-sources=URI-MULTIPLE --enable-sinks=ENCODE_FILE --options=pipeline.hmaudio.enable=1`
    - Fake sink (no UI): `bazel-bin/src/apps/hstream-cli/hstream-cli -g <game_id> --enable-sources=URI-MULTIPLE --enable-sinks=FAKE --options=pipeline.hmaudio.enable=1`
    - Explicit two-stage debugging: add `-c configs/ds_hockey_configure_stitching.yaml -c configs/ds_hockey_app_config.yaml`.
    - Multi-sink (comma-separated): `... --enable-sinks=RENDER,ENCODE_FILE`
    - All commands support an optional time limit: append `-t N` (or `--time-limit=N`) to stop after processing `N` seconds of video.
- Run a test binary (pattern):
  - `bazelisk run //src/libs/scoreboard:scoreboard_test`

Notes:
- This repo assumes CUDA/DeepStream/OpenCV and other system headers are installed; see `WORKSPACE.bazel` for local_repository paths (e.g., DeepStream under `/opt/nvidia/deepstream/deepstream`).
- Some DeepStream components have extra runtime shared-lib deps (e.g. tracker needs `libmosquitto1`).
- Game directories default to `$HOME/Videos/<game_id>`. Override with `HM_GAME_DIR=/path/to/games_root` (game dir becomes `${HM_GAME_DIR}/<game_id>`).
- Every default configuration value must live in, and be read from, `configs/baseline.yaml`. No compiled-in literal defaults, and no independent default set in a plugin, configurator, or UI: add the key to the baseline and resolve it, so one file answers what the shipped behaviour is. A value that genuinely has no sensible default must fail startup rather than silently pick one.
- The canonical default config is the bundled `configs/baseline.yaml`; keep it byte-for-byte synchronized with HockeyMOM's `hmlib/config/baseline.yaml`. Override explicitly via `HM_CONFIG_ROOT=/path/to/config` for development; invalid overrides fail startup rather than falling back.
- The desktop **Defaults** entry edits `~/.config/hstream-ui/defaults.yaml`, never the bundled baseline. Both backends load this user overlay between baseline and game `config.yaml`. Its presence replaces legacy tuning in `~/.hstream/hstream.yaml` while preserving legacy `paths` preferences; the legacy file remains untouched. The Defaults editor shows baseline plus this overlay; **Reset to Baseline** stages baseline controls, and Save Preset writes an empty map when nothing was changed afterward. Game selection retains game-local saving. Native tracker defaults may reference immutable user-owned tracker files alongside the overlay.
- Install Bazelisk once via `scripts/install_bazelisk.sh` (the `bld` script will prompt if missing).
- One-pass stitching delays `hmstitcher` output caps and buffer-pool allocation until the first input batch generates/loads control masks and reveals the actual stitched canvas size. If CUDA OOM appears in one-pass runs, inspect the runtime canvas dimensions and downstream caps/pool reallocation path rather than tuning guessed width/height padding.

## Coding Style & Naming
- Language: C++17 (see `.bazelrc`); format with `.clang-format`.
- Indentation: 2 spaces, no tabs; line length ≈ 120; left-aligned pointers; sorted includes.
- Bazel: use `cc_library` for reusable code and `cc_binary` for tools/tests. Prefer `INCLUDE_PREFIX` so includes look like `#include "hstream/src/libs/<mod>/Header.h"`.
- File names: `PascalCase` for classes/headers, `snake_case` for Bazel targets when consistent with neighbors.

## GPU Data-Path Guidelines
- Keep NVIDIA (CUDA/DeepStream) and AMD (HIP/VA-API) plugins and features in lock-step, including output overlays such as `hmrinkmap`. Changes to processing behavior, configuration, metadata, runtime controls, or plugin interfaces must include the corresponding implementation and regression coverage for both backends. Record backend parity and validation results in the PR; track existing AMD port gaps explicitly in `docs/amd-gpu.md`.
- AMD GPU validation is available on host `ripper`. Run AMD hardware tests there when the current host cannot run them. NVIDIA GPU checks may use `monster`, `mini`, or `meshy` when local hardware is unsuitable; Jetson checks use `stubby`.
- Keep video frames GPU-resident whenever possible. Avoid device-to-host (D2H) copies, CPU mapping/readback, and GPU-to-CPU-to-GPU round trips unless they are functionally required.
- Preview and display paths should prefer zero-copy GPU-native interop (for example NVMM/EGL/OpenGL/CUDA-compatible rendering) over conversion to system-memory images.
- When a D2H transfer is unavoidable, isolate it from the main pipeline, bound its frequency and resolution, and document why the transfer is necessary and what prevents a GPU-native path.
- Treat new system-memory caps, `gst_buffer_map`/`gst_video_frame_map` calls on video frames, CPU-side image conversion, and snapshot encoding in a steady-state video path as performance-sensitive changes that require explicit justification and measurement.

## Desktop UI

- Keep shared UI and features in the Qt desktop and HockeyMONWeb workspace in lock-step. Additions, removals and changes to shared features, layouts, tabs, controls, defaults, enabled states, dialogs, or runtime commands must include both interfaces in the same coordinated change. Update the generated web contract from this checkout, test both interfaces against the same native revision, and record the compared behavior and remaining gaps. Source fingerprints and matching screenshots alone do not establish workflow parity. See HockeyMONWeb's `docs/qt-web-parity.md` for the comparison gate and unfinished workflows; preserve its explicit limitations until both implementations and their behavior tests exist.
- Web-only service features, such as uploading games, authentication and storage quota management, do not need desktop counterparts. Shared controls, configuration and processing behavior affected by those features still follow the Qt/web parity rule.
- The browser may open desktop dialog workflows such as Highlights and Stitching Experiments in separate tabs. Preserve their controls, drafts and completion/cancellation behavior. When a workflow shares a GPU/backend with the original tab, enforce exclusive ownership on the server and disable conflicting actions in every tab until supervised cleanup releases it; browser-local state alone cannot protect the backend.
- Every action button and every tab in an application tab control must have an icon, including nested tabs and dialog tabs. Preserve existing control icons when porting Qt to the web, using the same artwork, meaning and colors. Keep icons through label changes, busy/disabled states and dynamically created controls; retain readable labels or accessible names. This rule concerns application tab controls, not the browser's own URL tabs.
- `ActionIcons.*` owns colored action artwork and the application tab/icon mapping. `//src/apps/hstream-ui:action_icons_export` renders the small browser glyphs; HockeyMONWeb's `tools/webapp/scripts/sync_stream_icons.py` verifies their native source provenance and, with `--exporter`, exact rendered bytes. Regenerate the web artwork and layout contract together when this catalog changes.

- Mouse-wheel and trackpad scrolling must never change dropdown, text/spin-box, slider, checkbox/radio, or tab values, even when the control has focus. Route wheel input over value controls to the nearest scrolling pane with `ValueControlWheel.h`; install the guard for each independent dialog, including dynamically created observation controls. Preserve deliberate wheel zoom on image canvases and scrolling inside opened dropdown lists. Values change through clicks, typing, or explicit keyboard input.
- Dialogs with preview windows must let the whole dialog resize and maximize. Use a normal Qt window type, a title-bar maximize button, a resize grip, and an in-dialog Maximize/Restore control as in Stitching Experiments. This applies to Highlights and Camera Experiments too. Put an icon-only Maximize/Restore control at the preview's top-right; Stop must restore the normal preview layout.
- Never drain posted events from inside a geometry write. `QCoreApplication::processEvents()` — and `QGuiApplication::sync()`, which calls it twice — delivers deferred deletes for objects Qt's own geometry machinery is still standing on, so calling either from `resizeEvent`, `moveEvent` or `setGeometry` frees them mid-use; the instance we hit was the animation `QMainWindowLayout` runs on the central widget. Waiting for the X server is not a reason to reach for them there, because requests on one connection are already processed in order; if a geometry write really does need the server to catch up, round-trip the XCB connection directly, as `sync_native_display()` in `HStreamWindow.cpp` does. Outside a geometry write `QGuiApplication::sync()` is fine — test drivers that want the full pump still use it.

Native preview widgets share `NativePreviewSurface`: while an external sink owns the pixels, resize/remap clears the X11 surface and native renderer children to black without pumping Qt events or reading video back. Ordinary Qt updates preserve rendered frames. A resized SIGSTOP-paused preview stays black until playback resumes.
`LetterboxRenderHost` keeps hidden preview widgets and their existing `QWindow` geometry synchronized; `NativeVideoTarget` restores its parent surface's full rectangle when shown. Preserve this across tab switches: deferred native resize events can otherwise restore the initial child-window size even when the letterbox is large.

## Testing Guidelines
- Keep tests small and colocated. Name sources `*Test.cpp` and targets `<name>_test`.
- Tests are simple binaries; run via `bazelisk run //<path>:<target>`. If using frameworks (e.g., Abseil), follow existing library deps.

## Commit & PR Guidelines
- Commits: imperative and scoped (preferred Conventional Commits). Example: `feat(stitching): improve synchronization for dual-camera`.
- PRs: include purpose, configs/commands used to validate, relevant logs/output or screenshots, and linked issues. Note any platform constraints (Jetson vs x86).
- Whenever referencing a PR, always write out its full URL visibly, including in progress updates and final responses. A PR number or linked label alone is insufficient.
- UI changes: include clearly labeled before-and-after screenshots in the PR description. Host them externally (for example, in a Gist); never commit screenshot files or add them to this repository's Git tree.
- PR default: open normal (ready-for-review) PRs. Only open draft PRs when explicitly requested.
- No AI attribution anywhere a PR is visible: titles, descriptions, commit messages, and PR comments. Drop generated-by footers, `Co-Authored-By` lines naming a model, and any mention of assistants, agents, or subagent reviews. Describe the change and how it was checked, not what produced it.
- Write like a person, not a manual. Short, direct sentences about this code and what it does; concrete numbers and file names over general principles. Skip the marketing adjectives, the tidy bullet triples, the bold section labels on every line, and the summary paragraph that repeats what was just said.
- Review cycle: after opening a PR, ask two high-reasoning Codex subagents to review the current PR in parallel when the subagent tool is available. Address actionable findings, then ask another two high-reasoning subagents to review the updated PR. Repeat this review/fix cycle until reviewers report no necessary fixes or only non-blocking suggestions remain; if reviewers or tools are unavailable or repeatedly stall, document that limitation and the completed validation instead of blocking indefinitely. Summarize each round's findings, fixes, and remaining risks in the PR or handoff.
- Dependency repins: PRs or follow-up updates that only change dependency commit pins do not require a new review cycle. This exemption also applies in related repositories. Keep the required build/test validation and record the dependency revisions in the PR.
- Related repositories: changes needed in HockeyMON, hm-cupano, and jetson-utils may be made in their respective repositories and submitted as PRs. If a repository is a fork, target `master` in the user's fork; otherwise, target `master` in that repository. Apply the same review/fix iteration requirements above to each PR. These review cycles may run in parallel with continued work in this hstream repository.

## Security & Configuration Tips
- Do not commit new large binaries (e.g., TensorRT `*.engine`); store externally and reference paths in configs.
- Verify local paths in `WORKSPACE.bazel` before builds; mismatches cause include/link errors.

## Jetson Notes
- Environment: JetPack 6.x with DeepStream installed at `/opt/nvidia/deepstream/deepstream`.
- Target split:
  - `--config=jetson`: Jetson-only build/cross-build path (Jetson sysroot/toolchain assumptions).
  - `--config=arm64`: non-Jetson ARM64/SBSA path (for example GB300), defines `AARCH64_IS_SBSA`.
- Cross-compiling:
  - Use `make jetson` for x86_64 -> Jetson cross-builds after syncing a Jetson sysroot (see `docs/jetson-cross-build.md`).
  - `make arm64` is for native non-Jetson ARM64/SBSA hosts, not x86_64 cross-compiles.
- Memory: build specific targets when RAM is constrained, e.g., `bazelisk build --config=jetson //src/libs/scoreboard:scoreboard`.
- Debug: use `--config=gstdebug` for GStreamer-heavy debugging builds.

## Architecture Overview

Coordinate request/receipt schemas, exporter flags, runtime protocols, and publication/cleanup changes across both repositories; run the web repository's `tools/webapp/scripts/sync_stream_contract.py --hstream-root PATH --check` and relevant integration tests against the intended native revision. The startup catalog check alone does not validate workflow operations or exporter capabilities.

Shared `ReplaySession::SaveTrial` marks an unbound export with `media.kind: none`, retaining recorded canvas/trajectory data without claiming a video identity. A chosen uploaded panorama is frozen and copied by the outer service as an owned input; native geometry and saved-trial validation remain authoritative. The match-editor operations return original PNGs and automatic-match identities, clone through the desktop editable-copy/edit primitives, and keep copy plus solve under one supervisor. Failed-source recovery regenerates immutable inputs and returns editable evidence without marking calibration complete. See `docs/web-workflows.md` for the request contract and limits.
  Browser Stitching Calibration uses the live `--stitching-calibration-only` graph and native WebRTC routes. This bounded crop transfer isolates incompatible Python/native TensorRT ABIs; full video frames remain in the Python GPU graph. See `docs/shared-ui-backends.md` for protocol and process ownership.

Each owns an independent processing stage. `AmdProgramGraph` connects the first five through owned frame-envelope metadata and runs crop in a second graph for each output submission. `program/AmdVideoStages` owns GPU panorama lifetimes and device-scoped destruction; shared `program/FrameGeometry` scales present followers into surface coordinates and resolves absent followers to the output aspect at render time; `ProgramRinkFilter` and `ProgramCamera` are independent metadata stages. The legacy synchronous processor is a qualification facade over the same libraries. The initial integration retains one-pair-at-a-time admission and existing source/audio/publication owners; it does not claim parallel frame execution or Pipeline-tab integration. Resolved configuration is supplied through the native embedding API; factories reject unconfigured startup. Header-only output handoff pins the source VA pool buffer while sharing its exact GPU memories, with no maps or pixel copies. See `docs/amd-gpu.md`.

### Dependency and distribution boundaries

- `scripts/side_by_side_video.py` is a standalone offline Python/FFmpeg comparison utility. It aligns relative playback times, fits two aspect-preserving panes within 7680×4320, and supports a shared start/duration. It does not enter the native playback or export pipeline; usage and timing limits are in the README.
- `WORKSPACE.bazel` pins `@hm` (HockeyMON's native `hockeymon/csrc/play_tracker`), `@hm-cupano` (panorama/CUDA mapping and blending), and `@jetson-utils` (GPU/video utilities). Changes in sibling checkouts do not affect these pins unless an explicit repository override is used. Inspect both the local adapter and the pinned external implementation for changes crossing these boundaries.
- External SDKs and libraries (DeepStream, CUDA/TensorRT, GStreamer, OpenCV, ONNX Runtime, Qt) are resolved through `WORKSPACE.bazel`, `bazel/`, and `buildfiles/third_party/`, using system inould pass before stallations or fetched dependencies as declared there. `//src/gst-plugins:hstream_runtime_plugins` supplies runtime plugin data; CLI/UI startup also configures plugin discovery for Bazel and installed runs. CLI/UI/exported-job launch caches must stage ONNX Runtime's CUDA/shared providers beside the core library for its relative dynamic loading. A linked application alone does not prove that the intended plugin `.so` is loaded.
- `scripts/make_deb*.sh` and `env/debian-package/` assemble `/opt/hstream` installations. `scripts/make_deepstream_deb.sh` backs the standalone `make deepstream-deb-ubuntu24`/`deepstream-deb-ubuntu26` targets: retain the downloaded amd64 package unchanged for 24.04 or apply the Docker builder's dependency relaxations for 26.04, with persistent outputs under `dist/ubuntu<version>`. See the README's package preparation instructions. Windows packaging in `packaging/windows/` runs the Linux stack in WSL; see `docs/windows-wsl-installer.md`. `scripts/publish_release.sh` owns the release matrix and may omit a platform through `make publish EXCLUDE=<platforms>`; two couplings constrain that set. The Jetson package is the only one carrying Hugin binaries, so its GPLv2 corresponding-source archives ship only with it, and `hstream-wsl.ps1` downloads the Ubuntu 24.04 package from its own release, so the installer cannot ship without it. A new release asset must join the explicit staged list that feeds `SHA256SUMS` and the upload, not a directory glob. Keep the x86, Jetson, and native ARM64/SBSA split described above when changing build or runtime paths.
- `scripts/hstream_instat_generate_team_only_reports.py` is an offline InStat PDF filtering utility. Debian packages install it under `/opt/hstream/scripts`, expose `hstream-instat-generate-team-only-reports` in `/usr/bin`, and declare its Python 3, Pillow, and Poppler dependencies. This exception does not add Python to native playback or calibration paths.
